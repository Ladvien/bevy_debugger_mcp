# 2026-10-21 merge: one crate, `bevy_fairy`

Focus: consolidation · Commits: f91c664..da090f1 · Outcome: fixes only (no release — the
first publish of a new name is the human's)

## Summary

The crate was two packages, `bevy_debugger_mcp` and `bevy_debugger_bevy`. The second name
stuttered, and a game that wanted the plugin had to depend on a crate whose name said it was
about the server. They are one product, so they are one crate now, named `bevy_fairy`, and the
repository is renamed to match.

The merge had one hard constraint: the plugin's guarantee that it cannot reach the operating
system. That guarantee used to rest on the plugin's *package* having a closed dependency list.
The package boundary died with the merge, so the guarantee had to be restated in terms of
features and re-enforced against the *resolved dependency graph*. It is now stronger than the
check it replaced: the ratchet runs `cargo tree` for the plugin's feature set and fails if
anything in it can synthesise an OS event, rather than trusting a list somebody maintains.

## Change: one crate

Plan: merge the plugin into the server package behind a feature, rename everything to
`bevy_fairy`, and keep the plugin's dependency closure free of the server's · Files:
`Cargo.toml`, `src/lib.rs`, `src/plugin/`, `src/server/`, `tests/`, `examples/`, every doc ·
Goal: one published crate, named `bevy_fairy`, whose plugin half a game can depend on without
dragging in the server · Proof: `tests/plugin_leaf.rs`, 3 tests.

Candidates considered:
- **One crate, features** (chosen) — the two names stuttered and the plugin was unreachable
  under a name that described the wrong half. Evidence: the user's direction. Effect: one
  published crate, one name, and a game compiles 319 packages instead of the server's ~700.
  Risk: the plugin's OS-boundary argument had to be rebuilt, because it rested on the package
  boundary.
- **Two crates, better names** — rename `bevy_debugger_bevy` to something that does not stutter.
  Evidence: the naming. Effect: fixes the stutter and nothing else. Risk: leaves two crates,
  two versions and two publish steps, which is what the direction was against. Rejected.
- **One crate, one feature set** — merge the plugin in and make it unconditional, so the
  plugin's code and the server's compile together. Evidence: simplest possible merge. Effect:
  one crate. Risk: a game that takes the plugin compiles `tokio`, `reqwest`, `axum` and the
  observability stack, and the plugin's dependency closure stops being a meaningful thing to
  check. Rejected: it would have cost the OS-boundary guarantee for nothing.

## Review

No independent review subagent was run, for the same reason as the previous iteration: the
host was under heavy load, and one measurement run was OOM-killed by the cgroup. The ratchet
did the reviewing here, and it rejected the merge three times:

1. `unused_mut` 7 → 9, from a `cfg`-gated `mut` binding that is unused when the feature is off.
2. A `rust` doctest in `src/lib.rs` that could not compile, because it uses `bevy` and the
   crate only has `bevy` under the `plugin` feature.
3. Two "new ignored tests", because a doctest became an `ignore` and the others' names changed
   when their files moved.

Each was a real defect and each is fixed. The first also uncovered a second bug in the same
function: with no feature enabled there was nothing to infer the element type from, so it did
not compile at all.

## Release and install

Version 0.2.0 → 0.2.0 (no bump) · semver-checks: not applicable, the name changed · Channel:
not published · Tag: none.

crates.io: https://crates.io/crates/bevy_fairy (not published) · Installed binary: rebuilt from
the tree.

**The release is blocked on the human, for a different reason than before.** The name
`bevy_fairy` is free on crates.io — 404 for both `bevy_fairy` and `bevy-fairy` — and
`cargo publish --dry-run` passes. But publishing a crate name for the first time is the
human's decision, and there is now only one crate to publish rather than two.

`bevy_debugger_mcp` 0.1.8 stays published. It is not yanked and will not be: the loop does not
yank, and a user who installed it keeps working. The README points at the new name.

**Also added: `.github/workflows/release.yml`.** There was no release workflow, so a publish
would have been a local one, depending on a token on this machine. The new workflow publishes
through trusted publishing: the tag triggers it, cargo exchanges the job's OIDC token for a
short-lived crates.io token, and no secret is ever stored in GitHub. It runs the ratchet, the
test suite, the doc build and a dry-run publish before it uploads anything, and it refuses a
tag that does not match the manifests' version.

Setting it up needs one thing only the human can do: on crates.io, for the `bevy_fairy`
crate, add a GitHub trusted publisher pointing at `.github/workflows/release.yml`. Until that
is done, a tag push fails at the publish step with an authentication error, and the dry run
still passes — so a failure there is a configuration problem, not a packaging one.

## Deferred / open

  correctly and that the plugin's closure is clean; they cannot prove what a real game does.
- **No fixture game.** Same reason.
- **B-009** — the injected cursor emits no `CursorMoved`. Unverified; needs the fixture.
- **B-010** — no `input` tool and no `watch` tool.
- **B-011, B-012, B-013** — the dead code: `src/server/cli.rs` (426 lines, never compiled), the
  `--tcp` flag that accepts a connection and drops it, and about 60 unreachable public modules.
  The merge made this easier to see: the server's modules are now one directory.
- **B-019** — the `observability` feature does not compile (42 errors).
- **The server's `bevy` dependency** is now `default-features = false` with the features the
  server's own code needs added by `visual-debugging` and `bevy-reflection`. The full engine is
  what those two features turn on, so a game that takes the plugin never pays for it.
